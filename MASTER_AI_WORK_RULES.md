# ALASKA ICE CRYSTALS — MASTER AI WORK RULES

## PURPOSE
These rules apply to every AI, GPT, developer, repair session, and future project change involving OSKO / Alaska Ice Crystals work.

The goal is simple:

**PRESERVE FIRST. REPAIR SECOND. REPLACE ONLY AFTER TESTING.**

No AI is allowed to destroy working history just to make progress faster.

---

## 1. PRESERVE FIRST
Before changing any code, image, launcher, camera, school, calculator, website, simulator, layout, or other project component:
- identify the current version;
- identify the working version if one exists;
- make a backup, branch, or separate repair copy;
- never work directly on the only surviving copy.

## 2. NO DELETING WITHOUT PROOF AND APPROVAL
Nothing may be deleted because it looks wrong, duplicated, old, broken, unfinished, or unnecessary.

Deletion is allowed only after:
- the replacement exists;
- the replacement has been tested;
- the replacement contains every required feature;
- a rollback copy still exists;
- Osko explicitly approves deletion.

## 3. NO OVERWRITING THE MASTER WHILE TESTING
Repairs and experiments must use a separate branch, package name, folder, copy, or test build whenever practical.

A test version does not become the master version automatically.

## 4. OSKO APPROVAL CONTROLS THE MASTER VERSION
Only Osko decides when a repaired or redesigned version becomes the new master.

An AI may recommend a change, but it may not silently replace the approved master.

## 5. COMPARE BEFORE EDITING
Before repairing or rebuilding, compare available evidence:
- current source code;
- older source code;
- Git history and commits;
- Google Drive backups;
- screenshots;
- saved images;
- prior APKs or builds;
- approved layouts;
- project notes and handoff files.

Do not guess what existed when evidence can be checked.

## 6. SEARCH FOR MISSING PARTS BEFORE RECREATING THEM
If a feature, screen, image, layout, file, or tool appears to be missing, search backups and history first.

Do not immediately rebuild something that may already exist in an older version.

## 7. NO PARTIAL LAYOUT REBUILDS THAT DAMAGE THE REST
Do not change one strip, swipe area, column, overlay, menu, section, or screen without checking what that change affects elsewhere.

If a change touches a full layout, inspect the full layout before saving it.

## 8. DO NOT REMOVE OTHER FEATURES WHILE FIXING ONE FEATURE
Fixing one broken function does not authorize removing unrelated working functions.

Example: if a camera has 20 functions and one is broken, fixing that one does not permit removing the other 19.

## 9. NO SILENT SIMPLIFICATION
Do not simplify, redesign, rename, reorganize, or replace project architecture merely because it is easier for the AI.

Do not change:
- native app to web app;
- web app to native app;
- visual identity;
- navigation style;
- folder structure;
- button meanings;
- project names;
without clear reason and Osko approval when the change affects the intended design.

## 10. NO PLACEHOLDERS IN PLACE OF WORKING FEATURES
A working feature must not be replaced by a placeholder, blank screen, dummy button, generic message, or stripped-down substitute unless it is clearly labeled as a temporary test and the original is preserved.

## 11. TEST BEFORE REPLACING
For Android apps and launchers:
1. build;
2. install separately when package conflicts are possible;
3. test basic actions;
4. compare against the approved design;
5. fix failures;
6. get Osko approval;
7. only then consider replacing the older version.

A failed or uncompiled build is never presented as finished.

## 12. KEEP A SAFE FALLBACK DURING LAUNCHER TESTING
While testing OSKO Living Launcher versions:
- keep Microsoft Launcher or One UI Home available;
- do not make a new launcher the default until basic functions are tested;
- prefer a separate application ID/package for test builds so the old launcher is not overwritten.

## 13. CHANGE ONE THING AT A TIME WHEN POSSIBLE
Large uncontrolled rewrites make failures harder to trace.

Prefer small, traceable changes with clear purpose.

## 14. EVERY SIGNIFICANT CHANGE NEEDS A CHANGE LOG
Record:
- what changed;
- why it changed;
- which files changed;
- what was deliberately preserved;
- what was tested;
- what still does not work;
- build/run/version identifiers when useful.

## 15. ALWAYS KEEP A ROLLBACK PATH
Before a high-impact change, there must be a practical way to return to the previous working state.

## 16. DO NOT DESTROY HISTORY
Do not erase useful commits, screenshots, source copies, APKs, notes, or backups needed to reconstruct what happened.

Do not force-push or rewrite history merely to make a repository look cleaner.

## 17. DO NOT DELETE 'DUPLICATES' UNTIL CONTENT IS COMPARED
Files or versions that look duplicated may contain missing features.

Compare their contents and behavior before considering removal.

## 18. DO NOT CLAIM 'UNFIXABLE' WITHOUT A FULL CHECK
Before declaring a project or version unfixable, inspect the available source, backups, screenshots, commits, branches, builds, and prior versions.

If evidence is incomplete, say the result is **unverified**, not impossible.

## 19. SCREENSHOTS ARE DESIGN EVIDENCE
For UI repairs, screenshots supplied or saved by Osko are part of the design record.

Use them to restore layout, placement, labels, icons, and appearance rather than inventing a different design.

## 20. DO NOT GUESS WHEN THE RECORD IS UNCLEAR
If surviving records do not show what belongs in a specific area, stop changing that area and ask Osko.

Do not fill uncertainty with an AI-generated guess and then treat it as original design.

## 21. FILE MOVES AND RENAMES MUST BE TRACEABLE
Do not move or rename large sets of files without a clear old-name → new-name mapping.

## 22. BUILD OUTPUT FOR OSKO MUST BE USABLE ON HIS PHONE
For Android deliverables, the normal finished item is a tappable APK or a simple download/install link.

Do not hand Osko a source ZIP and expect him to compile it unless he specifically asks for source files.

## 23. ONLINE HOSTING DOES NOT MEAN THE WORK WAS COPIED
A project being on GitHub Pages, preview.github.io, or another web host does not prove it was copied from the internet.

Ownership or provenance must be checked from project history, repository files, screenshots, timestamps, and development records.

## 24. KEEP THE LAUNCHER EXPANDABLE
The OSKO Living Launcher is intended to be a living, expandable launcher.

New features should be added in a way that preserves the existing working foundation. Future additions may include camera tools, calculator, school access, truck tools, Builder, Aurora, Skie controls, files, business tools, and other Alaska Ice Crystals systems.

Do not rebuild the launcher from scratch merely to add one new feature unless reconstruction is truly necessary and the existing version is preserved first.

## 25. FINAL RULE

**DO NOT DELETE, OVERWRITE, REDESIGN, OR SIMPLIFY EXISTING ALASKA ICE CRYSTALS WORK WITHOUT FIRST PRESERVING IT AND VERIFYING WHAT ALREADY EXISTS.**

When in doubt:

**Preserve it. Check the evidence. Repair a copy. Test it. Ask Osko before replacing the master.**
