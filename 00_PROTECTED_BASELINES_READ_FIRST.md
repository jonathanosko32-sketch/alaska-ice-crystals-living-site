# OSKO LIVING OS — PROTECTED BASELINES — READ FIRST

This file exists to prevent future AI assistants, developers, or automated tools from damaging known-good OSKO Living OS work.

## Non-negotiable preservation rules

1. NEVER overwrite, delete, rename, replace, simplify, or "clean up" a confirmed working build just because a newer build exists.
2. The current confirmed working visual baseline is:
   `TEST/OSKO-Living-OS-FIRST-BUILD-v1-FIX8.html`
3. FIX8 is a protected fallback. New integration work must be created as NEW files/builds beside it.
4. Broken historical builds (including FIX7, FIX9, FIX10) stay historical. Do not reuse them as stable baselines.
5. Never silently change approved visual designs, property layout, custom truck identity, Alaska Ice Crystals branding, Aurora placement, or locked master references.
6. Do not stack fragile wrapper-on-wrapper patches onto the protected build. Use direct modules and a clean integration path.
7. Safety-critical robot/vehicle control must remain separate from convenience AI, voice, or cloud logic.
8. Never expose API keys, signing keys, passwords, secrets, or credentials in source, chat, logs, commits, screenshots, or handoffs.
9. Before calling any new visual build stable, verify required modules and run integration checks. If it fails, return immediately to the last confirmed working build.
10. Every new visual build sent to Osko must include the new tap-ready test link AND the protected FIX8 fallback link directly underneath.

## Change discipline

- One purposeful change set at a time.
- Preserve old versions.
- Prefer additive modules over destructive rewrites.
- Record what changed and why.
- If a requirement is unclear, preserve the current behavior and ask the smallest question needed.
- Never assume an old or unusual piece is safe to delete.

## Recovery rule

If a new build fails to load, breaks touch/pan/zoom, loses property elements, changes approved visuals, or behaves unpredictably: STOP. Do not keep patching the broken build blindly. Restore the last known-good state, isolate the failing change, test it separately, and only then continue.

This preservation policy is part of the OS architecture, not optional housekeeping.
