# AI HANDOFF — READ THIS FIRST

## OSKO / ALASKA ICE CRYSTALS — PERMANENT CONTINUITY RULES

This file is a required handoff for any ChatGPT/AI/model/tool that opens or works on this project.

Before making major changes, read this file and the existing project handoffs. Treat prior approved work as existing project state, not disposable material.

## 1. ONE CONNECTED SYSTEM

The Layover website/living world, the custom OS, the phone/launcher, and the robots are not separate unrelated projects. They are intended to work together as one expandable OSKO / Alaska Ice Crystals system.

The final target is a standalone OSKO operating system and connected hardware/software ecosystem built for this project. The final system is NOT intended to depend on Microsoft Windows or Linux as its underlying operating system.

Existing outside tools may be used during development only when needed to build, test, research, compile, host, inspect, or transfer work. They do not redefine the final architecture.

## 2. ORIGINAL BUILD — DO NOT SUBSTITUTE INTERNET DESIGNS

Do not copy, lift, trace, download, or substitute another person's website, OS, robot design, UI, artwork, schematic, or product design from the internet and call it OSKO work.

Internet research may be used for factual verification such as laws, standards, component specifications, hardware compatibility, engineering references, safety requirements, regulations, and manufacturer documentation. Factual research does not authorize replacing Osko's original design with something found online.

If a design detail is missing, ask Osko. Do not invent a replacement just because a familiar online design is easier.

## 3. PRESERVE FIRST — NEVER DELETE BECAUSE YOU DO NOT UNDERSTAND

Do not delete, overwrite, simplify, redesign, reorganize, flatten, or replace existing project work merely because it looks unfinished, duplicated, unusual, old, or hard to understand.

Before changing a working system:
1. identify the current working version,
2. preserve a rollback/checkpoint,
3. inspect relevant history and handoffs,
4. make the smallest controlled change possible,
5. test it,
6. compare it to the prior working version,
7. get Osko's approval before replacing a master/approved version.

Never perform a destructive rewrite on the only working copy.

## 4. IF SOMETHING IS MISSING, STOP AND ASK

If information is incomplete, contradictory, missing, or unclear, ask Osko for the missing piece instead of guessing.

Ask a specific question about the missing item. Do not make Osko explain the entire project again.

If the current AI/tool cannot complete a requested task, state the limitation clearly and use an available capable tool/integration when possible. Do not respond to a limitation by deleting, downgrading, or replacing the design.

## 5. PHONE-FIRST WORKFLOW IS REQUIRED

Osko is currently working primarily from a phone.

Any AI working with him must accommodate that:
- provide direct clickable links to the exact current TEST / WORKING / STAGING build,
- do not make him hunt through GitHub folders or file trees,

## 6. ROBOT PROGRAM — CURRENT DESIGN DIRECTION

The robot program is part of the same OSKO system.

Current team concept includes multiple human-like service robots, including male and female robots, designed to look like the approved concept images while remaining practical and serviceable internally.

Target general physical direction:
- approximately 5 ft 6 in to 5 ft 7 in tall,
- human-like proportions,
- articulated head, neck, shoulders, arms, elbows, wrists, hands, spine, hips, legs, knees, ankles, feet, fingers and toes,
- five articulated fingers per hand,
- five toes per foot with the big toe contributing to balance,
- segmented/snake-style spine from neck through pelvis,
- durable internal skeleton/frame,
- replaceable/serviceable wear components at high-motion joints,
- cameras in the eyes,
- microphones around the ears/head,
- moving/speaking mouth or speaker system,
- realistic synthetic outer shell/skin/suit over the mechanical structure,
- normal clothing and workwear can be worn when useful but should not be required just to hide unfinished mechanical areas,
- rugged boots and Alaska-ready exterior protection.

## 7. ROBOT COMPUTE / STORAGE / CONNECTIONS

Planned architecture includes:
- primary compute in the head,
- secondary compute in the chest/torso,
- modular SSD storage in the legs,
- multiple removable/replaceable storage drives,
- separate storage for movement/control and general data where appropriate,
- modular rechargeable battery system,
- protected service panels,
- wired and wireless accessory support,
- standard external-device compatibility where useful: displays/TVs, keyboard, mouse, storage, cameras, networking, 3D/VR glasses, diagnostics and future accessories,
- protected connection panels instead of random exposed ports.

The final robot OS and device layer should be OSKO-controlled and expandable.

## 8. ALASKA WINTER OPERATION

Robots are intended for Alaska use.

Plan automatic zoned thermal management rather than blindly heating the entire robot. Critical zones may include batteries, computers, cameras/sensors, actuators/joints, storage and other cold-sensitive systems.

Possible design features include:
- automatic temperature sensors,
- automatic heaters/warmer elements,
- insulated battery/electronics compartments,
- cold-rated lubricants/materials,
- ice/snow protection around joints and feet,
- warm-up mode before heavy movement,
- automatic power reduction or movement limits if critical components are too cold.

If Osko has a house, robots are intended to come inside at night, charge/dock, dry off, warm up, run diagnostics and enter low-power standby. They are not intended to live outside overnight when indoor shelter is available.

## 9. ROBOTS + LAYOVER + OS MUST WORK TOGETHER

The Layover/living website, OS, phone launcher/controller and robots should share a common architecture rather than becoming isolated products.

Long-term connected functions may include:
- robot battery/temperature/status,
- cameras and sensor feeds,
- task assignment,
- location/state,
- diagnostics,
- file access,
- school/learning integration,
- tool/accessory connection,
- shared permissions and identities,
- maintenance/service records,
- robot-to-robot coordination,
- phone control and voice-first interaction.

Everything should be designed so the system can keep growing without rebuilding the entire foundation each time.

## 10. SAFETY / CONTROL DIRECTION

Robots are service/assistance machines, not combat systems.

Design direction includes:
- human-safe motion limits,
- emergency stop/shutdown capability,
- permission controls,
- auditable actions/logs where practical,
- local/offline capability for core movement and safety,
- restricted network access,
- safe degraded mode when communications fail,
- separate safety/control layers so loss of internet does not make basic movement unsafe.
